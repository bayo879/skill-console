# dsh-skill-console

DSH 的**技能控制台**：一个设置分区，管两件事——两个技能根里的技能**开/关**，以及 GitHub **技能仓库订阅**（添加/编辑/更新/删除订阅，手动拉取、挑选安装、备份回滚）。面板头部显示插件当前版本号。

面板位置：**设置 → 技能控制台**（`settings.section`，`order: 14`）。

---

## 为什么需要它

DSH 自己不带技能管理界面，于是有几件事只能手工做：

| 需求 | 没有面板时 | 本插件 |
| --- | --- | --- |
| 临时关掉一个技能 | 手动把 `SKILL.md` 改名或搬走（还得记住改回来） | 一个开关，只重命名发现文件 |
| 看某个技能到底从哪加载的 | 在 4 个目录里判断同名文件谁生效 | 直接标出生效者与被覆盖者 |
| 装第三方技能仓库 | `git clone` 后手工挑目录复制 | 订阅仓库 → 拉取 → 勾选安装 → 可回滚 |
| 更新已装技能 | 自己 diff、自己备份 | 变更预览 + 覆盖前自动整份备份 |

关键前提：DSH 的 filesystem provider 只认**精确文件名**（`SKILL.md` / `<name>.md`），并且只在技能根下**扫一层**。所以「关技能」最干净的做法就是给发现文件加一个 `.disabled` 后缀——内容零改动，DSH 当它不存在。

---

## 功能

### 技能 tab

- **一屏就是当前工作区的全貌（0.6.0）**：`/catalog` 缺省返回全局技能与项目技能两个源，这一屏直接列出两个技能源块（全局在前）、各带两级折叠（根头 / 仓库组头），**0.9.0 曾在后面平行多一块只读的「可用仓库」，0.10.0 已撤掉**——库搬去「技能仓库」页签，这里只留一个带计数的入口（点它跳到库视图）；「只看全局 / 只看项目」的**范围开关已在 0.6.0 删除**，想看别的工作区就换节顶的工作区下拉，而不是换范围。
- **两个技能根全都可见可写**：全局 `<DSH_HOME>/skills`、项目 `<projectRoot>/.dsh/skills`（受 `DSH_HOME` 影响）。`.agents` 目录不在本插件的管理面内：不扫描、不加载。面板上不显示任何具体目录地址，只显示根名与工作区名（**同名工作区例外**：下拉里补最短能区分的目录尾段，见下文「已知边界（刻意不做的事）」）。
- **按工作区切换**：工作区列表来自 DSH 的 **`workspaceRegistry`**——注册过的工作区都在，**不管它有没有活着的会话**（这正是 0.6.0 修的现场问题：没开过会话的工作区以前在下拉里根本不存在）；注册表拿不到、`list()` 读失败或没返回数组时退回「活着的会话」并按项目根去重，界面据此标明列表可能不完整。项目根 = 工作区目录向上找第一个含 `.git` 的目录（一路到根都没有就退回目录本身）。下拉里一项一个工作区、显示注册表给的名字（缺省是目录名），选过的按目录路径认领；没带当前会话时回落到最近一个会话，并在界面上**显式提示**——不会让你以为在管 A 其实在管 B。这个「当前工作区」是**整屏共享**的：技能 / 技能仓库 / 角色三个页签看的是同一个，在任一页签切换，另外两个跟着一起变——**切工作区只此一处**，技能页签不再有自己的范围开关。
- **同名覆盖关系讲清楚**：多个根里同名且都启用的技能，面板标出谁能生效、谁被压住（技能详情卡里也直接给出这一条的同名优先级）；关掉生效的那份，会告诉你接下来由谁接管。
- **诊断**：缺 `description`、`name` 不合法、frontmatter 围栏缺失/未闭合、读文件失败，逐条按码展示（见 `docs/HTTP-API.md` 的诊断码表）。
- **明细行显示所属仓库**：订阅装来的显示 `owner/name`，本地技能显示「本地（非订阅）」；技能简介不再内联占位，改到**悬停气泡**里（气泡里同时带安装 commit 与仓库内路径）。
- **软链接技能只读**：重命名会落到链接目标里去，所以面板显示它、但不给开关（`toggleable: false`）。
- **按仓库分组 + 两级折叠**：技能页签里同一个订阅仓库的技能收进同一个组（仓库名 + 组内技能数），本地（非订阅）技能单列一组、固定排在最后。**技能根头与仓库组头各自都能折叠**，都用组头左侧的三角按钮；折叠只把行藏起来，**没有任何批量按钮**（0.8.0 把「全部启用 / 全部停用」整层撤了：批量绕过单个技能确认、误伤面太大，逐项开关才是唯一入口）。折叠状态**按「工作区 + 技能根」记在 `sessionStorage` 里**：默认全部展开，切页签、刷新页面都还记得；存储不可用（隐私模式、被禁用）时降级成不记忆，折叠功能照常。
- **删除 / 移到可用仓库（破坏性，先备份）**：删除前先把整份技能备份好（目录包整包、扁平单文件、软链只存链接本身），备份成功才动盘、失败**一个字节都不删**；「移到可用仓库」把技能复制进 `<DSH_HOME>/skill-console/library/` 再删原处那份（原处是全局根或项目根都行），删原处失败**不回滚**、如实报告并留 `warning`；技能根本身永远不删。**这个按钮只出现在「当前角色没在用、库里也没有同名」的技能行上**（0.8.0）：已经在角色里、或已在库里的技能不必再搬，行上直接标出 `当前角色` / `可用仓库` 的来源标识。
- **技能仓库一页两视图（0.10.0）**：「订阅」与「可用仓库」是同一件事的两面（订哪些源 / 手里有哪些技能），合成一个页签，页内分段控件切换（`订阅 3` / `可用仓库 24`，计数带在标签上）。库视图三件事：按名字或简介**筛选**（纯客户端，不发请求）、按订阅来源**分组折叠**（本地的单列一组排最后）、行内「详情」/「同步到项目」。订阅卡片上的汇总行 `可用仓库：共 N 个技能 · 已同步 X · 待更新 Y · 上游已删除 Z` 从死文本变成入口——点它直接切到库视图并只看这个来源。库视图里**已在当前项目的技能不再出「同步到项目」**（那条路一定失败：安装从不覆盖），改标「已在项目」。
- **角色页一直显示差异（0.10.0，需求 ②）**：每个角色一行，折叠态就有**构成条**——一格一个技能、**顺序与展开清单逐行对应**（是清单的小地图），颜色只表达对项目的影响方向（已就位 / 会生效 / 会失效 / 库里没有 / 改不了），下面一行计数只写非零项；**非激活角色同样显示**（前缀「若切换：」），于是不激活也能横向比出两个角色各要动多少。展开 = **差异清单**（不是编辑器）：「会执行」在前，`missing` 与 `skipped` 收成后缀组「不会被执行」单列——这两类永远不会被执行，混进「会生效」就是界面版的谎。「按此差异切换」贴在清单下，确认框降级成一句话，危险动作终于有可核对的面。想改角色再点「编辑」进草稿。
- **「已对齐」不再说谎（0.10.0）**：对齐判据从「只看 `steps`」改成 `steps` / `missing` / `skipped` **三者全空**才算 `matched`（判据收敛在 `verdictOf`，`/roles` 与 `/roles/preview` 共用）。旧判据下「角色要一个库里根本没有的技能」和「要的技能在库里是软链、根本复制不了」都显示**已对齐**——一件都没做。同时 `/roles` 里**每个角色**都附上自己的 `plan`（逐技能差异），界面不必再猜；非激活角色的徽标从「未启用角色」改成「未激活」（以前拿一个角色的局部状态去描述整个项目）。
- **可用仓库进技能页签 + 分发到项目（0.9.0；0.10.0 把入口搬到技能仓库页签）**：`GET /catalog` 缺省响应平行多一块 `library`（只读分发源，只列不可启停；`scope=global|project` 的收窄响应一个字段都不多）；`POST /library/install` 把库里那份**复制**进当前工作区的项目技能根并启用，**从不覆盖**（项目已有同名一律 `copied:false, reason:'localKept'`，停用态也不动）；`/skill` 的**读**围栏扩到库根（仅详情），**写**围栏与冲突计算一个字没改；`GET /roles` 的候选补 `description` 与 `installed`，角色编辑页因此能显示所属仓库与明细。

### 仓库 tab

- **订阅**：`owner/name`、`https://github.com/owner/name`、`git@github.com:owner/name.git`、带 `/tree/<ref>/<subdir>` 的网页地址都能解析；可另填 `ref`（分支/标签/commit）与 `subdirectory`。
- **拉取即同步（0.8.0）**：`拉取最新` 刷新远端清单（写入 `repository-cache/`），**并顺手把清单里全部合法技能同步进可用仓库**——技能根一个字节都不动，但库跟着清单走。添加订阅、改分支/子目录、手动拉取，三条路都会自动同步，回执里带 `sync:{synced,unchanged,skipped}`；同步本身出错只回 `syncError`，不推翻已经拉到的清单。
- **可用仓库是链路的中间站**：「技能仓库 → 可用仓库 → 角色 → 项目」。库落在 `<DSH_HOME>/skill-console/library/`，DSH **不加载**它。已与清单一致的技能直接跳过（幂等）；被本地改过的默认跳过并如实列出原因，显式确认才覆盖、覆盖前一定整份备份；上游删掉的旧副本不会自动清理，卡片头只汇总「可用仓库：共 N 个技能 · 已同步 X · 待更新 Y · 上游已删除 Z」。
- **变更预览**：展开订阅卡片能看到每个技能在**可用仓库**里的状态（已同步 / 待更新 / 缺失 / 被改动 / 上游已删除），以及文件级 `added / modified / removed` 预览。
- **安装端点不再由面板暴露（0.8.0）**：`POST /repositories/install`（含 `target:'project'`）仍然存在，但界面上的勾选、安装目标选择器与安装按钮**整块撤掉**了——要往项目里放技能，走「角色切换」；要往可用仓库放，走订阅自动同步。这条能力只留给 API 调用方，契约测试仍在守它。
- **备份与回滚**：每次覆盖都留一份备份，可查看并恢复到任意一版（恢复前会把当前版本再备份一次）。
- **一行一个订阅、可折叠**：每个订阅是一张卡片，卡片头就是那一行仓库信息（地址、分支、子目录、上次拉取、状态汇总）。技能明细长在**它所属的那个订阅下面**，点卡片头（或左边的展开/收起按钮）就能收起；头部有「全部收起」。收起只是藏起来，明细都留着，再展开立刻就有内容。
- **管理订阅**：卡片头三个动作——`编辑`（改分支/子目录，改完自动重拉清单并同步）、`拉取最新`（刷新远端清单并同步进可用仓库）、`移除订阅`（删除）。收起状态也能用：收起不等于不能操作。
- **编辑 ≠ 换仓库**：`owner/name` 是订阅的身份，编辑只改分支与子目录；换仓库请移除后重新添加。
- **卸载订阅 ≠ 删技能**：移除订阅只删订阅记录，已安装的技能原样留在磁盘上。
- **勾选与安装目标已撤（0.8.0）**：仓库卡片不再有逐项勾选，也没有「装到全局 / 装到项目」的选择器——订阅只管把技能同步进可用仓库，「进项目」由角色切换负责。

### 角色 tab（把一组技能存成名字，一键对齐）

- **角色是「技能名的命名组合」，全局共享**：一份 `<DSH_HOME>/skill-console/roles.json` 存所有角色，跨项目复用；角色只记技能名，不记路径。
- **可以切换当前工作区**：节顶工作区条上的下拉决定「要操作哪个工作区」；切换后，角色列表、对齐状态与「切换到此角色」全都作用在选中的那个工作区上（与技能 tab 共用同一个当前工作区）。
- **切换（`切换` 按钮）严格对齐项目技能根**：角色里的启用、项目里其余的全部停用；角色里要、项目里没有、**可用仓库里有**的技能会先**复制**进项目根（`action:'copy'`，复制出来一律是启用态）。同一个角色在不同项目切换，各项目得到的是「本项目里该开的开、该关的关」。
- **角色的候选只有可用仓库**：编辑器列出的是可用仓库（`<DSH_HOME>/skill-console/library/`）里的技能，与当前工作区**彻底解耦**——项目技能与全局技能都不出现在候选里。勾选 = 切换时把它复制进当前工作区；行首的 `●` 表示本项目里已有同名且已启用、`○` 表示本项目里没有或没启用（只是信息，不参与勾选）。还没同步过时给一句「去技能仓库页签点同步」的引导。
- **项目里已有同名时保留本地（`localKept`）**：项目里已有同名技能就保留项目那份，**绝不被可用仓库那份覆盖**；这条只报告，不计入对齐动作数。
- **两边都没有的只提示（`missing`）**：角色里的名字在可用仓库与本项目都找不到时记 `missing`（多半是还没同步、或库里那份被删了），不算失败，但**会让状态变成「已偏离」**（0.10.0 起）——角色要一个库里根本没有的技能是永远无法达成的目标，报「已对齐」是假的。
- **编辑是草稿，只有「切换」才落盘**：新建/改角色只写 `roles.json`，一个技能文件都不碰；预览（`GET /roles/preview`）也只读不写。
- **偏离角色不自动纠正**：手工改过开关、或上游动了技能目录，面板就显示「已偏离」，等你自己再切一次——不会偷偷帮你改回来。

## 五条设计边界

1. **关技能只重命名发现文件**（`SKILL.md` ↔ `SKILL.md.disabled`、`<name>.md` ↔ `<name>.md.disabled`）。内容不改、文件不删，手工改回去就恢复——不依赖本插件还装着。另有两条**显式的破坏性动作**：删除技能、移到可用仓库——两者都**先整份备份再动盘**，可从 `GET /backups` + `POST /restore` 恢复；备份失败时一个字节都不改。
2. **拉取不等于安装（但 0.8.0 起，「拉取」= 刷新清单 + 同步进可用仓库）**。拉取只写清单缓存与可用仓库，**技能根一个字节都不动**；往技能根里放技能只有三条路：技能 tab 的逐项启停（只重命名）、角色切换的 copy（只往项目根），以及 0.9.0 起的「从可用仓库同步到项目」（把库里那份**复制**进当前工作区的项目根并**启用**，同名一律保留项目那份）。
3. **安装目标可选全局根或当前工作区的项目技能根**：缺省写全局 DSH 技能根（`<DSH_HOME>/skills`），显式 `target:'project'` 时才写当前工作区的项目技能根（`<projectRoot>/.dsh/skills`）；装到项目**不更新订阅快照**。**0.8.0 起面板不再暴露这条通路**（勾选与安装块已撤，端点仍在），日常由角色切换把技能放进项目。「移除订阅」依旧只删订阅记录，一个已装文件都不动。
4. **角色切换只写项目技能根，全局根在结构上不可达**。`applyRole(projectRoot, plan)` 的入参就只有项目根，没有「顺便改一下全局」的分支；可用仓库那份只被**读**（`copy` 的来源），角色链路既不读也不写全局根。想改全局技能，只能自己去技能 tab 逐个点。0.9.0 的「同步到项目」同理：目标也恒为当前工作区的项目根，请求体里没有 `target`。
5. **可用仓库与技能根是两回事**：`<DSH_HOME>/skill-console/library/` 是角色候选与复制来源的存放处——DSH **不加载**它，它不进 `resolveRoots()` / `findCollisions()`，也不能被启停 / 删除。0.9.0 起它在界面上**可见**（只读分发源）：行内动作只有「详情」与「同步到项目」，没有启停开关。0.10.0 把这块从技能 tab 搬到**「技能仓库」页签的第二个视图**（与订阅同一个页签，分段控件切换）——「订了哪些源」与「手里有哪些技能」是同一件事的两面。本插件不提供库的管理界面与自动清理。

**写身份是工作区目录路径**（0.6.0）：八个写接口（装到项目、切换角色、取消角色、移到可用仓库、启停技能、
删除技能、批量启停、从可用仓库同步到项目）从请求体 `project` 拿**工作区目录的绝对路径**。给了 `project` 就只认它——不是存在的
目录就 400 `error.workspace.invalid`，**绝不回落到请求头会话**（界面上选着工作区 B、写却落到 A 是最坏的
结果）；只有 `project` **缺席**时才按 `x-skill-console-session` 头严格解析，解析不出即 400
`error.role.noProject`。两种失败都**一个字节都不写**——**绝不回落到「最近一个会话」写到别处去**。
读接口仍宽松：给了 `project` 同样按目录路径严格校验（无效即 400），没给才回落，并在界面上标出「回落」。
`POST /repositories/sync`（0.7.0）与它带动的自动同步是**唯一不读工作区**的写通路：库是全局的，一次同步
服务所有工作区，所以它刻意不看 `project`、也不带会话头。

## 安装

插件是**本仓库里的源码**，用 `link:` 装进 profile（改代码不用重装，重启即生效）：

```bash
DSH_HOME="$HOME/Library/Application Support/dsh-desktop/harness" \
  "$DSH_HOME/.desktop-bin/node" \
  "/Applications/DSH Desktop.app/Contents/Resources/app/node_modules/@deepseek-ai/dsh/lib/bin.js" \
  plugin --profile web add \
  "link:/Users/zhanbaiyang/Documents/code/ai/agents/dsh/skill-console/dsh-plugin"
```

## 平台坑（改这个插件前必读，每条都是现场踩出来的）

1. **未 inject 的服务，读属性就抛，`?.` 救不了。**
   cordis 对未声明 `inject` 的服务，在**取属性那一刻**抛
   `cannot get property "webRuntime" without inject`——不是返回 `undefined`，
   所以 `ctx.webRuntime?.trustedHosts` 照样炸。可选服务只有一种正确读法：
   `ctx.get('webRuntime', false)`（核心能力、不需要 inject，缺失时回 `undefined`）。
   去重读法见 `http.js` 的 `trustedHostsOf()`；`test/contract.mjs` 用代理 ctx
   忠实复刻了这个守卫，任何「未 inject 的属性读」都会让离线测试失败。
2. **handler 里逃出去的异常，宿主 webserver 会回一个没有正文的 400。**
   面板那边只能显示「接口没挂上」，排查成本极高（第一次现场验证就是这么挂的）。
   所以宿主入口最外层兜底把任何异常转成 `500 {ok:false, code:'error.internal'}`，
   保证**每个响应都是带 code 的 JSON 壳**。
3. **`/api/skill-console` 会盖住 `/api` 那道 cookie 鉴权门。**
   `webServer` 是最长前缀优先，插件路由比 RPC 通道的 `/api` 更具体，于是请求
   直接进本插件（线上实测：无 cookie `curl` 其他已装插件的 `/api/*` 也拿 200）。
   结论：本插件的门只有自己的回环围栏，见下面「围栏不是认证」。
4. **客户端 bundle 的注册 id 必须等于包名**（`/plugins/<包名>/client.js`，
   行 id 反而是 `skill-console`）。四个身份标识互相对不上时，插件会**静默不加载**
   且 DSH 不报错，只能靠测试守——见 `test/contract.mjs` 的「身份标识一致性」一节。
5. **`webRuntime` 只提供 `{lanAddresses, trustedHosts}`**，由 `dsh-web-app` 用
   `webServer.host` + 它自己的 `trustedHosts` 配置算出来；本插件只读不算，
   免得两份受信名单漂移出安全口径差。

## 已知边界（刻意不做的事）

- **没有自动更新、没有轮询**。DSH 里没有可靠的定时器宿主面，而且「技能被静默换掉」比「手动点一下」危险得多。
- **备份不会自动清理**。目前靠用户手动删目录；加自动清理＝需要一个明确的保留策略，等有真实诉求再说。
- **上游删掉的技能不会自动删本地**。只标 `upstream-deleted`，删不删由人决定。
- **不解析完整 YAML**。只认顶层 `key: scalar`、成对引号、`|`/`>` 块标量；嵌套结构只跳过。真正的加载行为以 DSH 的 provider 为准，本插件只负责「展示 + 诊断」。所以可能出现「面板说合法、DSH 仍加载失败」的边缘 case——那时以 Agent 侧报错为准。
- **仓库根不是技能根**。`subdirectory` 必须指到放技能的那一层（含 `<name>/SKILL.md` 或 `<name>.md`）；指向单个技能目录会得到空清单（DSH 也不把根级 `SKILL.md` 当技能）。
- **根级 `.md` 文档不算技能**。扁平候选（基目录下深度 1 的 `<name>.md`）只有 frontmatter 合法才收进清单：一个 `.md` 说明不了它是技能，订阅 monorepo 根时 `README.md` / `CONTRIBUTING.md` / `CLAUDE.md` 之类会全被卷进来，装不了也删不掉（现场事故：`juliusbrussee/caveman` 的 11 个根级文档刷出一屏「frontmatter 不合法」）。目录候选不受影响——真有 `SKILL.md` 就是真技能，它坏了要留在清单里让人看见，那是上游的问题。拉取成功却 0 技能时，详情区会直接提示「技能可能在子目录里」。
- **围栏不是认证，而且它是这条路由上唯一的门**。DSH 的 `/api` RPC 通道本身有「绑定 authority 的签名 cookie」鉴权，但 `webServer` 是**最长前缀优先**，所以 `/api/skill-console` 会盖过 `/api` 的那道 cookie 门（已装的其他插件同样如此，已实测：无 cookie 直接 `curl /api/<plugin>/...` 会拿到 200）。也就是说本插件的写接口靠的是自己的回环 + `Host`/`Origin`/`sec-fetch-site` 校验加写操作标记头，防的是 DNS-rebinding 与跨站请求，**不是**身份认证。把 DSH 用 `--host 0.0.0.0` 暴露到局域网时，任何能连上的人都能调这些接口——那时不要依赖这道围栏。
- **工作区下拉里只显示工作区名，不显示绝对路径**（上文技能 tab「两个技能根全都可见可写」那条「面板上不显示任何具体目录地址」的延伸，也是从现场问题来的：一排一模一样的绝对路径根本没法选）。重名时补上**最短能区分的目录尾段**——先试最后一段，还不够就往上加，所以括号里**可能不止一段**（`/x/one/shared` 与 `/y/two/shared` 会显示成 `shared（one/shared）`、`shared（two/shared）`）。只补到能分开为止（加满 7 段仍分不开的极端情形才退回整条路径），地址平时不整条给；节顶工作区条上依旧只有一个名字，区分只发生在下拉里。
- **另一个技能管理器用的是「策略停用」，本插件用的是「改名」**。本机活动 profile 里，`dsh-skill-filesystem` 被 `dsh-web-app` 的补丁 `disabled: true` 关掉了，实际在提供技能的是 `@michengai/dsh-skills-manager` 自己的 provider（`dsh-skills-manager-external`）。它停用技能是往自己的状态文件里写策略（日志原话「本地策略，源文件不变」），本插件则是把 `SKILL.md` 改名成 `SKILL.md.disabled`。两种机制**可以叠加**：改名之后它的 provider 根本扫不到 `SKILL.md`，所以技能确实不会被 DSH 加载（它的发现规则也是「目录里得有 `SKILL.md`」，已核对实现）。但两边的**显示**会不一致——它按策略停用的技能，在本插件看来仍是「已启用」（因为文件没动）。这是两个独立管理器共存时无法消除的差异，刻意不读它的私有状态文件去对齐。
- **GitHub token 只用于提高限流额度**：`DSH_SKILL_CONSOLE_GITHUB_TOKEN` 或 `GITHUB_TOKEN`。面板只回报「有没有配」，不回显值。
- **可用仓库没有管理界面，也不会自动清理**（0.7.0；0.9.0 起「可见」但仍不可管理；0.10.0 起在「技能仓库」页签的库视图里浏览，可筛选、可按来源分组）。`<DSH_HOME>/skill-console/library/` 只能靠订阅同步写入，面板只让你**浏览**它（行内动作只有「详情」与「同步到项目」），不提供删除 / 停用它的入口（它不在技能根列表里、也不进冲突计算，唯一的出口是「同步到项目」把库里那份复制进项目根），也没有自动清理；上游删掉的技能不会从库里清走，所以卡片上的汇总里，「共 N 个」可能大于「已同步 + 待更新」——**以已同步与待更新为准**。
- **移除订阅不删库里的文件**。`移除订阅` 只删订阅记录；已同步到可用仓库的技能会原地留下（角色仍能用它们），要清只能自己删目录。
- **面板撤下的两条通路，端点仍在**（0.8.0）。`POST /repositories/install`（含 `target:'project'`）与 `POST /toggle-batch` 都还在路由表里、还有契约测试守着，只是界面不再调用：安装块整块撤掉（往项目里放技能改走角色切换），根头/组头的批量启停整层撤掉（逐项开关才是唯一入口）。删除它们要单独一次清理，且会连带删掉一批测试。
- **「移到可用仓库」不是无条件按钮**（0.8.0）。它只在「技能是可复制的普通技能、且当前角色没在用、库里也没有同名」时出现——已经由角色管理的技能没必要再搬，库里已有同名会 409。判定用的是 `/catalog` 每行新增的 `inRole` / `inLibrary` 两个布尔。
- **角色排除不掉全局技能**（0.7.0 起角色根本不看全局根，但结论没变）。角色只能管项目技能根：它既不停用全局技能，也不再从全局复制。真正的坑在同名：停用项目的同名副本后，**全局那份会接管生效**——角色想让某个技能彻底不生效却做不到（除非去技能 tab 手工关全局那份）。`/roles/activate` 会把这种情况逐条报在 `takeover` 里，但不代为处理。
- **`dsh-plugin/lib/client.js` 单文件 2000+ 行是 DSH 加载机制的结构性代价，不是没重构**。`dsh.client` 的面只服务**一个文件**（`/plugins/<包名>/client.js`），没有构建步骤、没有 bundle 入口，拆成多文件就得自己造一层运行时模块加载——比一个长文件危险得多。既然拆不动，就只能靠**内部分区**（常量、模型、视图、样式各成段，靠分段注释和契约测试守边界）。这条与「单文件超 2000 行就该拆」的常规原则冲突，冲突的根因在 DSH 那边的加载模型。
